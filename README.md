# Лагерь Pathfinder — Telegram-бот

Рабочая первая версия на том же стеке, что Botopros: Python 3.12+, aiogram 3.30,
SQLAlchemy, aiosqlite, SQLite, APScheduler. Код Botopros и его токен не изменены.

## Первый запуск на этом компьютере

Рабочая папка: **C:\Users\Maxim\Documents\GitHub\camp-bot**.

1. Откройте эту папку в Проводнике.
2. Дважды нажмите **«Запустить бота.cmd»** (или `Start.cmd`).
3. При первом запуске дождитесь установки зависимостей. Для неё нужен интернет.
4. Когда появится `Бот @... запущен; управление только в ЛС`, откройте своего
   нового бота в Telegram и отправьте **/start**.
5. У вас появятся **Жители / Лагерь / Начать сессию / Управление**.

**Пока бот нужен, оставляйте окно запуска открытым.** Для остановки нажмите
Ctrl+C в этом окне. После перезагрузки компьютера запустите тот же файл ещё раз.
Два окна одновременно открывать не нужно. Установка зависимостей повторяется
только при изменении requirements.txt; правки событий и баланса её не запускают.

Для применения обновлений кода остановите работающее окно через Ctrl+C и снова
откройте «Запустить бота.cmd». Уже записанное состояние лагеря сохранится.

Служебные сообщения планировщика об успешном запуске каждые 10 секунд отключены.
Предупреждения и ошибки остаются. Файлы журнала находятся в `logs` (при DATA_DIR —
внутри него): текущий `camp-bot.log` и до трёх предыдущих файлов `.1`–`.3`,
по 5 МБ каждый, суммарно около 20 МБ. Старые файлы заменяются автоматически.
При необходимости каталог можно переопределить переменной `LOG_DIR`.

В вашем `.env` уже указаны:

- мастер: `464396208`;
- группа: `-1003338522867`;
- тема: `24`.

Токен в этой папке уже заполнен. Если переносите проект на другой компьютер,
впишите **токен отдельного бота** в `BOT_TOKEN` файла `.env`.
Добавьте нового бота в группу и разрешите ему публикацию в указанной теме.
Игрокам нужно открыть ЛС с новым ботом и нажать `/start`.
Запускайте только один экземпляр процесса с этим токеном.

Если запуск завершился с ошибкой, окно останется открытым. Пришлите текст
ошибки, **не содержимое .env и не токен**. Проверка настроек при запуске не
показывает токен. Локальную подготовку без подключения к Telegram можно запустить
из PowerShell:

```powershell
cd C:\Users\Maxim\Documents\GitHub\camp-bot
powershell -ExecutionPolicy Bypass -File .\Start.ps1 -PrepareOnly
```

Для разработчика также поддерживаются `python -m bot.main` и
`python bot/main.py`, как требует bothost.
Без токена приложение завершится с понятным указанием заполнить `BOT_TOKEN`.
Токен не нужно присылать в чат или добавлять в Git.

Проверка экономики без токена и без Telegram:

```powershell
& .\.venv\Scripts\python.exe -m bot.simulate --days 7
```

## Как пользоваться

### Игрок

В ЛС доступны три постоянные кнопки: **Персонаж**, **Лагерь**, **Действие**.
Карточка игрока показывает только доступные лагерные занятия, их ранг и текущий
выбор. Полный список импортированных навыков и недостающих модификаторов виден
только мастеру. Сообщения оформлены компактно: строки внутри блока без пустых
промежутков, заголовки и важные значения выделены жирным. Пустые строки отделяют
разные смысловые блоки.
В теме 24 доступны две команды для любого участника: **`/camp`** выводит актуальное
состояние лагеря, **`/who`** — текущие занятия выбранных персонажей игроков и НПС
с долями времени; отдыхающие тоже включены. Команды не меняют состояние лагеря. Остальные
команды и кнопки управления в группе игнорируются. Отчёты отправляются в
заданную тему, без кнопок управления лагерем.

1. «Персонаж» → «Новый персонаж»: имя либо JSON из Foundry.
2. Мастер получает уведомление. До одобрения занятия недоступны.
3. Мастер назначает доступные занятия и навыки, одобряет персонажа.
4. Нажатия занятий накапливают веса: охота, охота, золото → 2/3 и 1/3 времени.
   Счётчики на кнопках не отображаются, доли показаны в тексте. Сброс очищает всё.
5. Через 5 минут после последнего изменения публикуется выбранный набор занятий
   и список работающих жителей. Изменение только долей не создаёт новой публикации.

У пользователя может быть несколько персонажей, но одновременно в экономике
участвует только выбранный. Во время начавшейся сессии выбор и смена персонажа
закрыты; мастер открывает их перед следующим периодом.

«Статистика» считает последние **28 игровых дней**, а не календарный месяц.
Для ресурсов показано произведённое количество, включая возможный избыток склада;
для морали — фактический положительный прирост, распределённый по вкладу работников.

### Мастер

Вместо меню игрока: **Жители**, **Лагерь**, **Начать сессию**, **Управление**.
Права проверяются по `MASTER_IDS`, в том числе на каждом callback: нельзя
получить права мастера, подделав кнопку.

- **Жители**: заявки, создание НПС, импорт навыков, назначение и удаление занятий,
  ранг и модификатор, имя, общий рабочий бюджет, доли занятий, одобрение.
  Рабочий бюджет позволяет сохранить половинную занятость исходных НПС;
  100% для полноценного работника выставляется там же.
- **Начать сессию**: число игровых дней → список назначений → подтверждение.
  Изменение назначения или баланса после показа списка делает подтверждение
  устаревшим. После расчёта отчёт попадает в очередь темы, и игроки сразу могут
  менять занятия на следующий период.
  Повторное нажатие одной кнопки не считает период заново.
- Уровень жизни, политики закупок, численность, расположение, постройки.
- **Активная проверка**: отдельные кнопки расхода компонентов и материалов,
  расчёт особой трапезы, произвольное изменение ресурса с описанием результата.
  Мастер вводит фактический расход и подтверждает его. При нехватке ничего
  не списывается. Повторное подтверждение не списывает второй раз.
- Ресурсы меняются **сразу после подтверждения**, без ожидания начала сессии.
  Мастер получает новые остатки в ЛС, а в тему лагеря сразу ставится отчёт
  с изменениями и блоком **«🏕️ Состояние лагеря сейчас»**. Тот же блок есть
  в результатах личных событий. Меню «Лагерь» всегда читает текущие значения.
- Последнюю активную проверку можно отменить, пока после неё не менялся лагерь.
  Позже нужна новая явная корректировка, чтобы не отменить чужие последующие траты.
- Выгрузка состояния, журнала и версий правил — из панели управления.

Ввод обычной трапезы: число обычных ингредиентов на порцию, особых на порцию,
порций. Например `2 1 3` списывает `3 × (2 × 0,1 + 1) = 3,6` компонента.
Мастер нажимает её **после** успешной проверки готовки. Мораль прибавляется один
раз, не за каждую порцию; при нулевом провианте бонус не применяется.
Эффекты конкретного рецепта для едоков бот не разыгрывает.

### Постройки и переезд

Стоимость, вложенные материалы и еженедельное содержание каждого объекта вводит
мастер. Содержание добавляется к базовому расходу материалов. Предложение
«всем зданиям автоматически по 2 материала» **не принято и не включено**.
Также не включено отвергнутое предложение «первый работник морали только удерживает».

При переезде стационарные постройки разбираются и возвращают 40% материалов,
переносное имущество сохраняется целиком. При отдельном демонтаже переносного
возвращается 100% его вложенных материалов. Содержание не возвращается.
Возврат ограничен ёмкостью склада. Отдельной платы и ограничения частоты переезда нет.
Заметность сбрасывается к числу жителей. Постройки с одинаковым названием не
объединяются; каждую можно отдельно разобрать.

Механические бонусы кухни, частокола, палатки первой помощи и т.п. применяет
мастер на сессии. Бот не делает броски Pathfinder и не устанавливает произвольные
цены на эти объекты. Улучшение пока вносится как отдельный объект с собственными
затратами и содержанием; автоматического дерева улучшений нет.

## Баланс без пересборки

Все числовые правила находятся в **config/rules.json**.
После редактирования мастер нажимает **Перечитать баланс JSON** в ЛС.
Ошибочный файл отклоняется, действующие правила сохраняются.

- `modifier_scale`: сейчас `0 → 0%`, `+5 → 40%`, `+10 → 67%`, `+15 и выше → 100%`.
  Между точками линейная интерполяция. НПС и игроки считаются одинаково.
- `yield_high`: недельный вклад одного человека с 100% эффективности и времени.
- `weekly`, `prices`, `buy`: содержание, цена процентного пункта/единицы, закупки.
- `lifestyles`: стоимость жизни, множитель работы над моралью, заметность.
- `morale`: нелинейность, убывающая отдача от работников, сроки и штрафы.
- `items`, `production`: общий склад формул, уровни, вероятности и цикл.
- `action_skills`: лишь подсказки мастеру при выборе навыка (отмечены ★).
  Это не обязательное сопоставление. В частности, готовку можно назначить через
  нужное вам знание вместо Crafting; заработок — через подходящее Lore.
- `npc_seed` и `initial` используются **только при создании новой базы**.
  При перезагрузке они не перезаписывают текущий лагерь и жителей.

Профит «мало/средне/много» из исходных настроек НПС перенесён в модификаторы
`+5/+10/+15`. Это начальная миграция, а не утверждение о реальных листах НПС.
Мастер может заменить их импортированными навыками.

После изменения недельных расходов/ёмкости проверьте калибровку: для еды,
компонентов и материалов `4 × yield_high − недельный расход = ёмкость` при
20 жителях, без закупок, дополнительных построек и активных трат.
Содержание построек закономерно замедляет восстановление материалов.

Каждая рассчитанная сессия сохраняет версию применённых правил. Код не читает
Google Sheets во время работы. JSON — самостоятельный снимок согласованной модели;
последующие изменения таблицы надо переносить в него явно.

### Игровое время

Экономика пересчитывается **по дням** внутри указанного периода: 21 день за раз
эквивалентен 21 шагу по одному дню при тех же назначениях, правилах и случайности.
В отличие от агрегированных строк исходной таблицы это учитывает хронологию
закупок, голода, казны и производственных циклов. Реальные сутки ничего не
прибавляют к ресурсам и не запускают производство.

Мораль: четыре сильных работника на комфортном/хорошем уровне с 0 до 100 за
28 игровых дней; на роскошном — за 7, при достатке еды и денег. Следующий работник
даёт меньший вклад. Возле 100 рост замедляется, при низкой морали спад ускоряется.
Без работников стоимость жизни не даёт бонуса или штрафа морали, но неоплаченное
содержание остаётся отдельной причиной падения. Нулевой провиант всегда приводит
к спаду (при 0 морали ниже нуля не опускаемся).

Неснижаемая заметность — 1 процентный пункт на жителя, максимум 100%.
Работа кроме морали добавляет небольшой шум, пропорциональный доле времени.
Снижение заметности лагеря тоже создаёт этот шум, затем вычитает свой полезный вклад.

### Пассивные предметы

При запуске цикла выбирается скрытый день готовности: 1-й — 10%, каждый из
2–7-го — по 15%. Поэтому вероятность готовности к дню 7 — 100%.
Промежуточные циклы считаются, но их предметы уже кем-то взяты и не выводятся.
Выдача показывается только если цикл завершился в **последний рассчитанный день**.

| Компоненты | Выдача |
|---|---|
| <30 | Ничего, сообщение о нехватке |
| 30–<50 | Один 1-го уровня |
| 50–<70 | Два 1-го уровня |
| 70–<90 | Два 1-го + один 3-го |
| 90–100 | Два 1-го + два 3-го |

При 50–100 с вероятностью 50% один предмет 1-го уровня заменяется предметом
2-го уровня. Внутри уровня предметы равновероятны. Дополнительных компонентов
за выдачу не списывается: производство уже входит в пассивный расход.
Палатка алхимика не нужна. Все 25 ранее перечисленных версий включены.

## Импорт Foundry PF2e

Обычный экспорт Actor JSON поддерживается, но часто содержит **только ранги**:
итоговые модификаторы система рассчитывает во время игры с учётом предметов,
правил и эффектов. Такие значения бот отмечает как отсутствующие и не угадывает.

Для точных значений:

1. В Foundry создайте Script macro с содержимым `foundry/export-camp-skills.js`.
2. Выберите токен персонажа (или используйте назначенного персонажа пользователя).
3. Запустите макрос и отправьте полученный `camp-skills.json` боту.
4. Мастер выбирает подходящий навык для каждого доступного занятия и одобряет.

Из JSON сохраняются только имя, ранги и модификаторы навыков. Биография,
предметы, секретные заметки и исполняемый код из файла не сохраняются и не выполняются.
Ограничение загрузки — 5 МБ. Поддерживаются современные ключи и старые `sur/cra/ste`.
Варианты домов/модулей Foundry могут требовать ручной корректировки мастером.

Основание для формата: [исходные данные PF2e Character](https://github.com/foundryvtt/pf2e/blob/master/src/module/actor/character/data.ts)
и [расчёт характеристик персонажа](https://github.com/foundryvtt/pf2e/blob/master/src/module/actor/character/document.ts).

## Реальные ежедневные события

Подписка по умолчанию выключена. Для подписчиков после 19:00 Europe/Moscow
делается одна попытка в реальные сутки с вероятностью 50%. Дата попытки
сохранена в базе: перезапуск не даёт второй попытки в тот же день.
Игровой календарь при этом не продвигается. Результат выбранного события сразу
изменяет текущие ресурсы лагеря и записывается в журнал, видимый через «События
лагеря». Ответ приходит в ЛС; отдельный отчёт без кнопок отправляется в тему 24
группы лагеря. В нём указаны название события, имя персонажа, выбранное действие,
успех/провал, полный художественный текст исхода и фактические изменения ресурсов.
После них выводится полное состояние лагеря на момент применения результата.
Вероятности и модификаторы остаются в личном ответе.

Пример сообщения в теме:

> 📜 Событие лагеря: Песня у костра
>
> 👤 Персонаж: Герра
> 🎯 Действие: Пообщаться с жителями
> ✅ Результат: успех
>
> ────────────────
>
> Беседа начинается с жалоб на мокрые сапоги, а заканчивается историями, над
> которыми смеётся весь круг. Даже давние спорщики дослушивают друг друга до
> конца. Когда костёр догорает, расходиться по палаткам никто не торопится.
>
> ────────────────
>
> 📦 Изменения в лагере
> 🔥 Мораль: +3 п.п.

Пропущенные и устаревшие события в тему не отправляются. Каждое завершённое
событие ставится в очередь публикации один раз, вместе с записью результата.
Повторные нажатия и перезапуск не создают новую награду или новую запись очереди.
События, завершённые до добавления публикаций в группу, задним числом не рассылаются.

В `config/events.json` включены **36 событий**: три пользовательских и 33 созданных
по аналогии и одобренных в списке на согласование. Читаемая версия с развязками:
**docs/events.md**. Награды прогулки Сайфера не были заданы: для первой версии предложены
`+5 п.п. провианта` за охоту и `+3 компонента` за находки; оба провала без последствий.
Файл перечитывается автоматически, пересборка не нужна. `origin` различает
пользовательские и сгенерированные сюжеты; `reward_note` поясняет пробные награды.

После ручного изменения JSON читаемую копию можно обновить командой
`python scripts/export_events.py`. Бот использует только JSON, а не эту копию.

Событие выбирается равновероятно из всего каталога, **без фильтрации по навыкам
и пассивным занятиям**. Получатель должен быть подписан и иметь выбранного
одобренного персонажа. Событие привязано к этому персонажу: смена персонажа
не заменяет проверяющего. Полученные варианты и известные модификаторы сохранены
в базе; редактирование каталога не меняет уже выданное событие.

- Кнопка «Пройти мимо» / «Не участвовать» завершает событие без броска,
  изменений ресурсов, статистики или записи в журнал лагеря.
- Любой другой вариант делает одну проверку. После первого ответа другой
  вариант выбрать нельзя; повторные нажатия показывают тот же результат.
- Вероятность успеха — перевод модификатора через `modifier_scale` из rules.json:
  `+10 → 66,67%`, `+15 и выше → 100%`. Ранг владения не даёт отдельной прибавки.
- Сложная проверка (`penalty: 0.15`) вычитает **15 процентных пунктов**:
  `66,67 → 51,67%`, максимум `100 → 85%`.
- Если задан `critical_chance: 0.07`, эти 7% резервируются независимо от навыка:
  максимум успеха **93%**. При +10: успех 66,67%, критический провал 7%,
  обычный провал 26,33%. Такое правило применяется у костра; в остальных
  событиях критического провала нет, если явно не добавить его в JSON.
- Если вариант допускает несколько навыков, используется известный навык с
  наибольшим модификатором: например, Выживание или охотничьи знания.
- В 24 часа от выдачи событие истекает. При нажатии — **«Событие уже устарело»**.
  Сроки, выбранные ответы и результаты переживают перезапуск. Не доставленные
  вовремя события из очереди уже не отправляются.
- Нехватка золота не создаёт долг: при потере 10 и остатке 3 списывается 3.
  Запасы и мораль ограничены ёмкостью, заметность — минимумом по населению.
  В результате показываются фактические изменения.

В импорт добавлены Восприятие и Lore. Макрос Foundry теперь включает Восприятие
отдельно. Мастер также может открыть **Жители → Навыки событий** и добавить или
исправить навык без назначения пассивного занятия: `perception 2 15`.
Если итоговый модификатор не указан, бот не угадывает его и не расходует событие:
можно пройти мимо или попросить мастера заполнить значение. Если значение было
неизвестно при выдаче, его разрешено заполнить до ответа; известные значения
остаются зафиксированными.

Структура варианта в каталоге:

```json
{
  "label": "Разговорить незнакомца",
  "skills": ["diplomacy"],
  "penalty": 0.15,
  "success": {"text": "Вы договорились о награде.", "effects": {"gold": 10}},
  "failure": {"text": "Незнакомец украл кошелёк.", "effects": {"gold": -10}}
}
```

Событие содержит `id`, `title`, `text`, `choices` и необязательный `skip_label`.
Весь каталог проверяется перед использованием: некорректный файл не блокирует
обычные отчёты и публикации выбранных занятий.

## Деплой, как у Botopros

### bothost / Docker

Есть Dockerfile и Procfile. Команда: `python -m bot.main`.
В панели задайте переменные из `.env.example`, в том числе
`DATA_DIR=/app/data`. Этот каталог должен быть подключён к **постоянному тому**.
База относительного `DB_PATH` будет создана внутри DATA_DIR.
Изменения JSON тоже храните в постоянном томе либо в репозитории; для внешнего
JSON можно установить абсолютные `RULES_PATH` и `EVENTS_PATH`.

### VPS / systemd

```bash
cd /opt/camp-bot
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# заполнить .env
sudo cp deploy/camp-bot.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now camp-bot
sudo journalctl -u camp-bot -f
```

Перед переносом сделайте резервную копию базы и JSON баланса. Для копии живой
SQLite используйте SQLite backup API либо остановите процесс и копируйте базу
вместе с её WAL-файлами. Из панели мастера доступна отдельная JSON-выгрузка для
просмотра и архива; автоматического восстановления из неё в первой версии нет.

## Проверки и границы готовности

Автоматические тесты проверяют экономику, импорт, права, кнопки через Dispatcher,
очередь с имитацией Telegram, повторные подтверждения, перезапуски SQLite,
одновременные изменения, игровые месяцы и ежедневные события.

Реальный Telegram ещё не проверен: для него нужен токен нового бота.
Перед использованием основной группы прогоните в тестовой теме:

1. `/start` у мастера и игрока: разные меню; в группе нет ответов на команды.
2. Создание персонажа → уведомление мастера → импорт/назначение → одобрение.
3. Охота, охота, золото: 66,67/33,33; через 5 минут одна публикация в нужную тему.
4. Изменение только долей: новой публикации нет, в том числе после рестарта.
5. Начать сессию на 7 дней: один отчёт, повторное подтверждение не продвигает время.
6. Перезапустить процесс: все запасы, подписки, таймеры и назначения сохранены.
7. Активное списание и трапеза: подтверждение, недостаток, повтор, отмена.
8. После окончания игры: открыть выбор занятий для следующего периода.
9. Включить события у одобренного персонажа: кнопки приходят только в ЛС.
   Пропуск не виден в журнале лагеря. Один ответ даёт один результат, старые
   кнопки не позволяют повторить награду или публикацию в теме. Отчёт в теме
   содержит персонажа, выбранное действие, текст исхода и ресурсы, без кнопок.
   Через 24 часа — «Событие уже устарело».

Ограничение Telegram: отправка сообщения и запись «отправлено» в SQLite не
являются одной транзакцией. При аварии ровно между ними возможна повторная
публикация сообщения. Экономика и списания от этого не дублируются.
